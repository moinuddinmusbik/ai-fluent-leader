## The Big Idea

The first AI agent job at your organization shouldn't be a new capability — it should be the repair loop your team is already running by hand. When Nate sorted 52 customer-support tickets by root cause instead of subject line, 39 of 52 were the same Slack-access failure repeated. 98% closure rate. Called it a great week. Never noticed they were efficiently cleaning up a mess they kept making.

His argument: don't automate the answer. Fix the path that keeps breaking. The question isn't "how do we close tickets faster?" — it's "why does this ticket exist at all?"

---

## The Framework: [[root-cause-first-then-agent]]

Nate names this process explicitly. Six-step sequence:

1. **Pull 50–100 recent operational cases** (support, IT access, finance exceptions — wherever the team keeps fixing the same thing by hand)
2. **Strip PII; group by root cause — not subject line** (what actually failed, not what was asked)
3. **Pick the largest category** as the agent's first job — boring and reversible over interesting and risky
4. **Write the process down before automating** — the documentation IS the agent's instruction set
5. **Keep human approval on access and money only** — everything else the agent prepares
6. **Scorecard it weekly** — count category recurrence, not closure rate

---

## How It Works

- The expensive part of a support ticket is reconstructing the customer's state across systems — not writing the reply. Agents attack reconstruction; humans handle judgment.
- 52 cases → 19 in a comparable week: the upstream Slack-access path was fixed (not just answered faster).
- 26 patterns found across 50–100 tickets; only 2 required upstream fixes to eliminate the majority of volume.
- **Gumroad case:** Agent found a charting bug → wrote the test → shipped the fix → got the design wrong. Only the customer could catch the design error. This defines the human-approval boundary: execution yes, design sign-off no.

## Receipts

- **51 of 52 issues closed** — 98% closure rate masked 39 identical Slack-access failures
- **52 → 19 cases/week** — 63% reduction by fixing path, not automating cleanup
- **26 patterns, 2 upstream failures** — root-cause sort across 50–100 tickets
- **Gumroad** — agent shipped a bug fix; customer caught the design error
- **Amazon customer-obsession frame applied:** "The minute somebody pays and can't get what they thought they bought, you have a support problem." Internal report waiter, locked-out colleague, chasing client — all live in the same gap between promise and delivery.

---

## What It Means For You

1. Run the root-cause sort this week: 50 tickets, strip names, group by what failed. Biggest group = agent's first job.
2. Write the process before automating. Documentation-first IS the instruction set.
3. Draw two bright lines: access and money require human approval. Set this as policy before deploying.
4. Change the scorecard: measure category recurrence week-over-week, not tickets closed.

---

## Mistake to Avoid

Measuring agent success by closure rate instead of recurrence rate. 98% closure masked 39 repeating instances of the same broken path. The metric: did this category appear less this week than last?
